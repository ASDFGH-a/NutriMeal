# Связи между частями кода

Здесь указаны фактические runtime-связи. Разделы, представленные только файлами и тестами, помечены отдельно от подключённых сценариев.

## Точки входа и композиция

```text
index.html
  -> src/ui/app/standalone-entry.js         # production runtime

app-preview.html
  -> src/ui/app/standalone-entry.js         # интеграционная проверка того же runtime
      -> createSeedCatalog()
      -> createCoreRepositories(localStorage, catalog.products)
      -> initializeCoreData({catalog, repositories})
      -> createDiaryServices(repositories.diary)
      -> createWaterServices(repositories.water)
      -> createCatalogServices()
      -> createPlanningServices({
           planRepository: repositories.plan,
           presetRepository: repositories.planPresets,
           nutritionSetRepository: repositories.nutritionSets,
           activeNutritionSetRepository: repositories.activeNutritionSet
         })
      -> createProfileServices(repositories.profile)
      -> createBodyHistoryServices({
           weightRepository: repositories.weightHistory,
           measurementRepository: repositories.measurementHistory,
           profileRepository: repositories.profile
         })
      -> UI flows: meal-add, mass-entry, planning, profile, statistics, settings
      -> app-router.js -> app-state
          -> screen-router.js -> render diary/catalog/planning/profile/statistics/settings

PWA_v60_code_blocks.html
  -> legacy runtime                         # fallback / референс
```

`application-bootstrap.js` создаёт shell, overlay и `app-state`. `standalone-entry.js` собирает реестр экранов и `app-router`; переход обновляет состояние, заголовок, активный пункт меню и вызывает соответствующий renderer через `screen-router`. Обработчик меню отдельно отменяет черновик выбора рецептов при уходе с этого сценария.

## Активные сценарии нового runtime

| Сценарий | UI-вход и связи | Данные и побочные эффекты |
|---|---|---|
| Инициализация | `standalone-entry.js` создаёт domain seed и `createCoreRepositories`, затем вызывает `initialize-core-data.js` с зависимостями | Загружает каталог, дневник, воду, профиль, план, историю тела, наборы, тему и настройки карточек; application layer не зависит от infrastructure |
| Дневник | `standalone-entry.js` → `diary-presenter.js` / `diary-screen.js`; действия записи из `meal-add-flow.js` | `diary-services.js` → diary use cases → diary repository; CRUD и массовые записи сохраняются |
| Массовая запись | `mass-entry-flow.js` → `diaryServices.massEntry.preview/apply`; callback раскрытия приёмов передаётся из `standalone-entry.js` | Mass-entry use case проверяет источник, даты и конфликты; apply сохраняет в diary repository, после записи из библиотеки UI раскрывает затронутые приёмы пищи |
| Вода | Обработчики дневника в `standalone-entry.js` | `water-services.js` → add/remove/restore use cases → water repository |
| Каталог | `meal-add-flow.js` → catalog cards/filters/editors/details в `catalog-modals.js`; `catalog-filters.js` domain helpers управляют выбором фильтров, пользовательскими категориями/значениями и каскадным обновлением связанных карточек; расчёт рецепта читает `calculateRecipeNutrition`; добавление из detail открывает выбор приёма и переходит к дневниковому flow | `catalog-services.js` → catalog use cases; products/recipes/collections меняются в памяти; detail actions управляют выбором, избранным, редакторами и добавлением в дневник |
| Настройки карточек | `meal-add-flow.js` → callback из `standalone-entry.js` | `catalog-card-settings.repository.js` сохраняет `nutrition-catalog-card-settings` |
| Планирование | `planning-flow.js` → экраны planning, модалки и выбор рецептов через `meal-add-flow.js`; подбор по пищевой группе использует domain `recipeMatchesFoodGroup` | `planning-services.js` → use cases и repositories плана, пресетов, наборов и активного набора; план и изменения сохраняются |
| Профиль | `profile-flow.js` → `profile-screen.js`, `profile-modal.js`; кнопка планирования открывает редактор | `profile-services.js` → `saveProfile` use case → `profile.repository.js`; профиль сохраняется под `nutrition-profile-v1`, после сохранения пересчитывается план |
| Вес и замеры | `profile-flow.js` → body-history modals и действия дневника | `body-history-services.js` → weight/measurement use cases → repositories; обновляются история, текущие параметры профиля и состояние экранов |
| Статистика | `statistics-flow.js` → `get-diary-statistics.js` и domain statistics | Читает переданное состояние дневника, воды, веса, замеров, профиля и наборов; отдельного statistics repository нет |
| Настройки и теория | `settings-flow.js` → settings/theory screens | Тема сохраняется через theme repository; справочные таблицы строятся из domain data |

Каталог фильтров и настройки отображения карточек находятся в `domain/catalog/` и infrastructure соответственно. Их UI подключён в preview; это не меняет in-memory характер продуктовых и рецептурных данных.

## Маршрутизация нового runtime

Все шесть доступных экранов зарегистрированы в `screen-router.js`; `app-router.js` использует `app-state` как источник активного маршрута. В preview проверены заголовки и активные пункты меню на каждом маршруте, а также выход из выбора рецептов без сохранения черновика.

## Основные зависимости слоёв

| Участок | Откуда → куда | Назначение |
|---|---|---|
| Bootstrap | UI → application services и UI-модули | Сборка состояния и сценариев запуска |
| Services | Application services → use cases, repositories, contracts | Поставка зависимостей и сохранение результатов |
| Use cases | Application → domain и contracts | Выполнение команд с явными аргументами и зависимостями |
| Repositories | Infrastructure → storage и domain normalizers | Чтение/запись состояния |
| UI flows | UI → services/use cases и domain read helpers | Обработка событий и отображение результата |
| Domain | Domain → только domain/shared | Предметные расчёты без DOM и localStorage |

`statistics-flow.js` вызывает statistics use case напрямую; отдельного statistics service нет, поскольку use case получает уже собранное состояние и не выполняет persistence. Остальные application services получают repositories из composition root и не импортируют infrastructure.

| `nutrition-sets.repository.js` | `nutrition-sets-v1` | Да |

Продукты, рецепты и подборки не имеют repositories или storage keys: в новом runtime это in-memory state, и обновление документации не подразумевает изменение этого решения.

## Legacy boundary

`index.html` запускает standalone runtime напрямую. `PWA_v60_code_blocks.html` сохранён как legacy fallback и референс; его удаление требует отдельного решения.
