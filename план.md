# План переноса NutriMeal на целевую архитектуру

## Текущая точка

Есть два runtime:

- `index.html` продолжает запускать PWA v60 через iframe. Он остаётся рабочей версией и референсом; production-вход не переключён.
- `app-preview.html` запускает новый runtime. В нём подключены дневник, каталог, статистика, тема и теория.

Новый runtime ещё не равен полному приложению: в нём отключены маршруты «Планирование» и «Профиль», а действия веса/замеров в дневнике недоступны. Наличие соответствующих domain/application/infrastructure/UI файлов не закрывает перенос их пользовательских сценариев.

**Последний полный результат тестов:** `npm test` — 170/170. Последний законченный интеграционный срез preview — каталог, включая фильтры, категории/теги и настройки карточек.

## Что уже сделано

| Этап | Результат |
|---|---|
| Основа архитектуры | Созданы `contracts`, domain-модели, use cases, services, repositories и UI-модули по областям |
| W1 — вода | Добавление, удаление и отмена удаления используют water services/use cases/repository |
| D1 — дневник | Добавление, пакетное добавление, изменение, замена, удаление и восстановление проходят через diary services/use cases/repository |
| M1 — массовая запись | Preview/apply, выбор источников и дат, режимы конфликтов и сохранение через diary repository реализованы и подключены |
| C1 — каталог | CRUD продуктов/рецептов, подборки, избранное и связанные действия подключены к catalog services/use cases |
| Каталожные фильтры | Фильтры и пользовательские категории/теги подключены в preview; управляются отображаемые атрибуты карточек |
| I1 — инициализация | `initialize-core-data.js` загружает seed и сохранённое состояние через repositories |
| S1 — статистика | Новый preview собирает запрос статистики через `get-diary-statistics.js` и показывает статистические экраны |
| Настройки | Новый preview подключает тему через repository и экран теории |
| P1 — планирование, слой данных | Модели, use cases, `planning-services.js`, repositories и UI-компоненты существуют; они не подключены к preview, поэтому пользовательский сценарий планирования ещё не перенесён целиком |
| Документация | Архитектура, дерево, связи и этот план сверены с текущими файлами и runtime-точками входа |

**Ограничение каталога:** продукты, рецепты и подборки хранятся в памяти и не переживают перезапуск. Репозитории и новый storage key для них не добавлялись. Персистентно сохраняются только настройки карточек каталога.

## Что осталось — пошагово

Работать по порядку. Каждый шаг проверять в `app-preview.html` как целый пользовательский сценарий и сравнивать с PWA v60; тесты модулей дополняют, но не заменяют интеграционную проверку.

### U1 — завершить новый runtime

1. **U1.1 — подключить планирование.**
   - Подключить `createPlanningServices` и актуальное состояние к preview.
   - Добавить работающий маршрут и связать его с существующими экранами/модалками.
   - Перенести полный сценарий: план и пресеты, библиотека наборов, создание/редактирование/удаление набора, редактирование недель и ориентиров, добавление рецептов и аналитика.
   - Проверить сохранение, отмену/ошибки и повторный запуск с теми же данными.
   - Готово, когда раздел не отключён и полный цикл сценария совпадает с референсом по поведению и UI.

2. **U1.2 — подключить профиль и историю тела.**
   - Подключить profile screen/modal и `createBodyHistoryServices`.
   - Включить сценарии профиля, веса и замеров; убрать disabled-действия из дневника только после подключения обработчиков.
   - Проверить сохранение, удаление/восстановление записей и обновление профиля/статистики после изменений.
   - Готово, когда данные доступны через новый runtime и после перезапуска, а интерфейс соответствует референсу.

3. **U1.3 — связать навигацию нового runtime.**
   - Подключить `app-router.js` и `screen-router.js` либо явно привести их к фактическому flow.
   - Убрать ручные обходные переходы и обеспечить единый маршрут для diary, catalog, planning, statistics, profile и settings.
   - Проверить активное состояние меню, заголовки, переходы из модалок/действий и возврат назад.
   - Готово, когда все разделы доступны без заглушек и состояние навигации не расходится с отображаемым экраном.

4. **U1.4 — интеграционная проверка полного набора экранов.**
   - Пройти основные пользовательские сценарии целиком в одном preview runtime, а не отдельно в искусственно урезанных формах.
   - Сверить визуальные состояния, модалки, пустые/ошибочные состояния, адаптивность и переходы с PWA v60.
   - Исправить обнаруженные расхождения и повторить регрессию.
   - Готово, когда все доступные в референсе ключевые сценарии имеют проверенный эквивалент в preview.

### E1 — переключить production-вход (только после U1)

5. **E1.1 — подготовить переключение.** Подтвердить, что полный UI и поведение нового runtime проверены; сохранить совместимость данных и текущих storage keys.
6. **E1.2 — переключить `index.html` на новый runtime.** Делать это отдельным последним изменением; не удалять legacy до успешной проверки.
7. **E1.3 — финальная регрессия.** Проверить запуск production-входа, основные сценарии, persistence и `npm test`; только после этого решать, можно ли удалять legacy runtime.

## Критерии закрытия этапа

- Кодовый путь сценария проходит через целевые слои; наличие файла/теста само по себе не считается готовой функцией.
- UI проверен вместе с действиями, сохранением и переходами; сохранены внешний вид и поведение PWA v60.
- Старые данные и ключи хранения не потеряны.
- Тесты проходят; документация и статусы плана обновлены.
- `index.html` остаётся на legacy до окончания U1 и готовности E1.

## Исходная декомпозиция проекта

Первоначальный план группировал работу по областям: данные и хранение; общие инструменты/локализация; каталог; профиль и план; наборы питания; дневник; массовая запись; статистика; UI и связывание. Текущий статус этих областей отражён выше по реально подключённым сценариям, а не по наличию модулей в целевой структуре.
