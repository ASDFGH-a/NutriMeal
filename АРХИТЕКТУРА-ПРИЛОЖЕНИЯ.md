# Архитектура приложения NutriMeal

## Назначение и текущая граница миграции

Этот документ описывает фактическое состояние кода, а не только целевую схему.

Сейчас в репозитории существуют два запуска нового runtime и отдельный legacy fallback:

- `index.html` — production-точка входа нового runtime из `src/ui/app/standalone-entry.js`.
- `app-preview.html` — отдельная точка интеграционной проверки того же runtime.
- `PWA_v60_code_blocks.html` — сохранённый legacy runtime, используется как референс и fallback.

Новый runtime включает дневник, каталог, планирование, статистику, профиль и историю тела, а также настройки. Все исходные пункты U1.1–U1.4 и E1.1–E1.3 закрыты, `index.html` запускает новый runtime. Дальнейшие решения, не входившие в этот этап, явно отделены в [плане](./план.md).

## Слои и обязанности

```text
index.html / app-preview.html
  -> UI composition root (standalone-entry.js)
      -> application services / use cases
          -> domain rules
          -> contracts
      -> infrastructure repositories -> localStorage
```

Это направление зависимостей — целевой принцип. Композиция сервисов и flows остаётся в `standalone-entry.js`; навигация нового runtime проходит через подключённые `app-router.js` и `screen-router.js`.

### Contracts

`src/contracts/` задаёт формы команд и результатов, проверки границ и storage-порт. Контракты не содержат предметных расчётов.

### Domain

`src/domain/` содержит модели и правила без зависимости от DOM и хранилища: питание и пищевые ценности, дневник, каталог, наборы питания, план, профиль, вода, история тела, статистика, даты и фильтрация. `catalog/catalog-filters.js` содержит сопоставление фильтров, формирование доступных значений, переключение и добавление выбранных значений, добавление фильтровых значений, преобразование выбранных значений в товарах/рецептах/фильтрах, каскадное переименование и удаление значений с синхронизацией карточек и выбранных фильтров, создание и переименование пользовательских категорий и очистку связанных данных при их удалении; `planning/plan.model.js` нормализует направление и величину коррекции калорийной цели; `nutrition-set/nutrition-set.calculations.js` сопоставляет рецепты пищевым группам и рассчитывает недельные цели, статистику макроцелей и сводку проблем состава; `statistics/diary-statistics.js` рассчитывает дневную аналитику, минимум/максимум воды, достижение частотных ориентиров пищевых групп, число микронутриентов с сопоставимыми нормами и заполненность обзорных замеров; `diary/diary-calculations.js` — масштабирование КБЖУ по граммам, прогресс суточных целей, итоги приёмов пищи и распределение суточных КБЖУ по приёмам. UI отображает готовые результаты.

### Application

`src/application/usecases/` реализует отдельные операции. `src/application/services/` связывает сценарии с репозиториями и предоставляет runtime-устройству вызовы более высокого уровня. `initialize-core-data.js` загружает seed-данные и сохранённое состояние.

Граница фактического подключения важна:

- `diary-services.js`, `water-services.js`, `catalog-services.js`, `planning-services.js`, `profile-services.js`, `body-history-services.js` и `initialize-core-data.js` используются production runtime и preview.
- `standalone-entry.js` создаёт infrastructure repositories через `createCoreRepositories` и передаёт их application services; `initialize-core-data.js` получает seed и репозитории через параметры. Application services не импортируют persistence-адаптеры.
- `get-diary-statistics.js` вызывается `statistics-flow.js` напрямую.
- Профильные изменения проходят через `profile-flow.js` и profile service; история веса/замеров — через `body-history-services.js` и соответствующие use cases.
- Данные продуктов, рецептов и подборок остаются в памяти; отдельные репозитории для них не добавлялись. В каталоге сохраняются только настройки карточек.

### Infrastructure

`src/infrastructure/persistence/` содержит адаптер хранения и репозитории. Репозитории сохраняют совместимые localStorage keys; доменные нормализаторы используются там, где это предусмотрено конкретным репозиторием.

### UI

`src/ui/` содержит каркас, экраны, модальные шаблоны, flows и форматирование. `standalone-entry.js` собирает новый runtime и связывает flows с сервисами. `app-router.js` обновляет `app-state` и передаёт выбранный маршрут, а `screen-router.js` вызывает renderer соответствующего экрана. Entry point оставляет за собой только перехват ухода из незавершённого выбора рецептов, чтобы очистить его черновик перед навигацией.

## Подключение сценариев в новом runtime

| Область | Что подключено в standalone runtime | Ограничение |
|---|---|---|
| Дневник | Просмотр по датам, CRUD записей и воды, массовая запись, история веса и замеров | Сценарии тела используют отдельные body-history services |
| Каталог | Рецепты, продукты, подборки, фильтры, пользовательские категории/теги, настройки карточек | Продукты, рецепты и подборки не сохраняются между запусками |
| Статистика | Статистика питания и тела, периоды и детальные представления | Использует загруженное состояние; собственного statistics repository нет |
| Настройки | Тема и раздел теории | Импорт/экспорт каталога обозначен как «В разработке» и не реализован в legacy |
| Планирование | План и пресеты; библиотека наборов; создание/редактирование/удаление наборов; недельные блюда и ориентиры; выбор рецептов и аналитика | Сценарии подключены через `planning-flow.js` и `planning-services.js`; ключевые сценарии сверены с референсом в U1.4 |
| Профиль / история тела | Редактирование параметров, активности, тренировок и пищевых ограничений; CRUD веса/замеров и отмена удаления | Подключены через `profile-flow.js`, `profile-services.js` и `body-history-services.js`; пересчёт плана и синхронизация профиля/истории выполняются при изменениях |

## Хранение данных

Подключённые репозитории используют следующие ключи:

| Данные | Ключ |
|---|---|
| Дневник | `nutrition-diary-v1` |
| Вода | `nutrition-water-v1` |
| Вес | `nutrition-weight-history-v1` |
| Замеры | `nutrition-measurement-history-v1` |
| Профиль | `nutrition-profile-v1` |
| План | `nutrition-plan-v2` |
| Пресеты плана | `nutrition-plan-presets-v1` |
| Наборы питания | `nutrition-sets-v1` |
| Активный набор | `nutrition-active-set-v1` |
| Тема | `nutrition-theme` |
| Настройки карточек каталога | `nutrition-catalog-card-settings` |

План, пресеты, наборы, профиль и история тела подключены к соответствующим flows/services и используют прежние ключи. Seed-каталог и состояние инициализируются `initialize-core-data.js`; продукты, рецепты и подборки после этого живут в памяти.

## Правила развития

1. Сохранять визуальное и функциональное поведение PWA v60; сравнивать законченные сценарии целиком, не считать наличие отдельных экранов завершённой миграцией.
2. Новую предметную логику размещать в domain/application, а не в обработчиках DOM.
3. Мутации проходить через use cases/services; работу с persistent storage — через repositories.
4. Не удалять legacy runtime до окончания финальной регрессии и отдельного решения.
5. Не вводить persistence для каталога без отдельного решения о требуемом поведении и совместимости.

## Проверка, зафиксированная при обновлении

Последний полный прогон: `npm test` — 202/202. В production `index.html` проверены запуск без iframe, мобильная навигация, переход по всем шести маршрутам и сохранение воды после reload; тестовое состояние localStorage восстановлено. В интеграционном preview полностью проверена мобильная массовая запись из библиотеки, включая применение и проверку записи на выбранной дате. Дополнительно в браузере проверены подбор рецептов по группе «Овощи», переключение значения фильтра, создание тега с автоматическим выбором, создание и переименование пользовательской категории, а также добавление, переименование и удаление её значения; настройки localStorage восстановлены. Все шесть маршрутов проверены на ширине 390 px и desktop; ошибок JavaScript и горизонтального переполнения нет. Все application services теперь получают repository ports из composition root и не зависят от infrastructure. Архитектурные тесты запрещают зависимости domain от внешних слоёв, application — от infrastructure/UI, а доступ к persistence в UI ограничивают composition root. Production-переключение выполнено; `PWA_v60_code_blocks.html` сохранён как fallback.
